# 北京时间用量统计准确性修复设计

## 背景与目标

每日 Token 柱状图统一读取 `usageDaily`。DeepSeek 的日数据来自平台 API，Codex 与 Kimi 的日数据来自本机 JSONL 日志增量扫描。现有实现存在四类准确性问题：Codex 相同累计快照会被重复计数；手动历史同步可能与后台日志轮询并发并重复累加；全量同步用固定 200 轮和“本轮记录数为零”判断结束，可能把未读完的日志当作成功；日键取决于操作系统本地时区，而业务要求固定按北京时间结算。

本次修复的目标是：

- Codex/Kimi 手动全量同步对同一份静态日志产生确定且可重复的结果。
- Codex 相同累计快照只计一次，并且去重状态跨扫描批次保存。
- 扫描只有在覆盖当前可读日志后才报告成功；未完成必须显式失败。
- 所有与每日统计有关的“今天、日期、保留窗口和默认年份”固定使用 UTC+8。
- 手动重扫失败时不留下半套日汇总或不匹配的游标。
- 不在升级或启动时自动重建已有数据；用户在修复后手动触发一次历史同步。

## 非目标

- 不引入数据库或长期事件索引。
- 不改变 Token 总量口径：总量继续包含缓存输入，缓存值作为总量的子集展示。
- 不自动修改、清理或重建用户现有的 `usageDaily`。
- 不改变 DeepSeek 平台返回的历史日期，只统一本地“今日”判断和查询月份。

## 方案选择

采用基于现有 JSONL 扫描架构的完整修复：扫描器提供明确完成状态，调度器提供同一 provider/channel 的独占执行入口，Codex 游标持久化累计快照标识，并将业务日历固定为北京时间。

没有采用仅提高扫描轮数的最小补丁，因为它无法解决并发重复、空记录批次提前结束和 Codex 源事件重复。也没有采用新数据库方案，因为本次准确性问题可在现有边界内修复，数据库迁移会扩大风险和实施范围。

## 组件设计

### 1. 北京时间日历

主进程增加无状态的北京时间工具，至少提供：

- `beijingDayKey(timestampMs)`：返回 `YYYY-MM-DD`。
- `beijingDateParts(timestampMs)`：返回北京时间的年、月、日。
- `addBeijingDays(dayKey, delta)`：按 UTC+8 的无夏令时日历增减日期。
- `retentionStartDay` 所需的北京时间窗口计算能力。

本地日志聚合、用量保留窗口、DeepSeek 今日数据选择、调度器当前查询月份、IPC 默认年份均改用这些函数。渲染端提供等价的轻量日历函数，柱状图最近 31 日、费用卡昨日和热力图今日指示不再依赖系统时区。

北京时间固定为 UTC+8，不读取 `getTimezoneOffset()`，也不受夏令时影响。测试会在 `TZ=UTC`、`TZ=America/Los_Angeles` 和 `TZ=Asia/Shanghai` 下运行相同时间戳，结果必须一致。

### 2. 扫描完成协议

`scanFiles` 除记录数组外返回本轮扫描元数据：

- `records`：本轮解析出的非重复用量记录。
- `complete`：本轮是否已经访问完扫描开始时发现的所有文件和可用完整行。
- `bytesRead`：本轮实际读取字节数，用于进度和诊断。

达到单轮 4 MiB 预算只意味着 `complete=false`，不代表错误。即使本轮没有用量记录，只要还有未访问的日志字节，全量同步仍继续下一轮。文件末尾没有换行的半行不作为当前可用完整记录；扫描器可以将本轮视为已覆盖当前完整行，后续文件追加换行后由增量扫描重新读取该半行。

`rescanLocalLogs` 以 `complete` 为唯一正常结束条件。保留可注入的安全轮数上限用于防止异常无限扫描和测试；达到上限且仍未完成时抛出带 provider 信息的 `LOCAL_LOG_RESCAN_INCOMPLETE`，UI 显示同步失败，不能生成成功摘要。

### 3. Codex 累计快照去重

Codex `token_count` 同时包含 `last_token_usage` 和 `total_token_usage`。解析器继续用 `last_token_usage` 形成该次增量，但把 `total_token_usage.total_tokens` 作为单调累计快照标识传给扫描器。

每个 Codex 文件游标从 `{ offset, mtimeMs }` 扩展为 `{ offset, mtimeMs, lastUsageTotal }`：

- 当前记录的累计值与 `lastUsageTotal` 相同：记录是重复快照，不进入 `records`。
- 累计值变化：记录正常进入结果，并更新 `lastUsageTotal`。
- 累计值下降：视为上游会话计数重置，当前记录正常计入并更新游标。
- 缺少有效累计值：保持兼容，按现有增量记录计入。
- 文件截断或轮换并从 offset 0 重读时，同时清空该文件的 `lastUsageTotal`。

游标在每个已提交完整行后同步更新，所以相同累计快照即使横跨两个 4 MiB 批次也能去重。Kimi 没有同类累计字段，不启用这条去重规则。

### 4. 同一通道独占执行

调度器把当前 `inflight` 集合升级为可等待的执行 Promise，并暴露同一 `providerId:channel` 的独占执行入口。现有定时轮询、手动刷新和历史同步都通过该入口协调。

历史同步在清除 provider 日汇总和游标之前取得 `codex:localLog` 或 `kimi:localLog` 的锁，并持有到该 provider 全量重扫完成或回滚。锁内的重扫直接调用日志读取器，不再次获取同一锁。后台 60 秒轮询在锁被占用时复用/等待当前 Promise，不启动第二个扫描器，因此不会读取并累加同一区间。

不同 provider 继续互不阻塞；DeepSeek API 轮询也不受本地日志锁影响。

### 5. 失败回滚与手动修复流程

每个 provider 开始手动重扫前，在内存中保存该 provider 的 `usageDaily` 条目和对应游标。重扫成功后保留新结果；任何扫描、解析、存储或未完成错误都会恢复旧条目和旧游标后再向上抛出。

回滚仅覆盖正在重扫的 provider，不触碰另外两个 provider 的数据。同步成功后现有 `pollAll()` 继续执行一次增量刷新，补上重扫期间新追加且已经形成完整行的日志。

应用升级后不自动重扫。用户手动点击“同步历史数据”时，Codex/Kimi 旧日汇总被安全重建；在此之前旧的多算数据保持不变。

## 数据流

1. 用户点击历史同步。
2. DeepSeek 按现有 API 历史流程同步。
3. IPC 为 Codex 取得 `localLog` 独占锁。
4. 保存 Codex 旧日汇总和游标，清空 Codex 工作数据。
5. 循环扫描 4 MiB 批次；扫描器按北京时间生成日键，并用游标累计值跳过 Codex 重复快照。
6. `complete=true` 后提交结果并释放锁；失败则恢复快照后释放锁。
7. Kimi 按相同步骤执行，但不使用累计快照去重。
8. 同步结束后执行一次常规刷新并通知渲染端重新读取 `usageDaily`。

## 错误处理

- 扫描安全上限耗尽：抛出 `LOCAL_LOG_RESCAN_INCOMPLETE`，包含 provider、轮数和已读字节数。
- 文件在扫描时消失：沿用现有容错，跳过并清理失效游标。
- 文件截断或替换：重置 offset 与 Codex 去重状态，从头读取。
- Store 写入或解析流程抛错：恢复该 provider 的旧日汇总与游标。
- 同步失败：设置窗口显示失败，不广播伪造的成功摘要。

## 测试设计

新增或扩展 Node 测试覆盖：

- 超过 200 个批次的模拟扫描仍继续到 `complete=true`。
- 一个读取了字节但没有用量记录的批次不会让全量同步提前结束。
- 达到安全上限且 `complete=false` 时失败并恢复旧汇总和游标。
- 两个并发的同 provider/channel 操作只执行一次底层扫描，历史重扫期间定时轮询不能进入。
- 同一 Codex 累计值在同批次和跨批次出现时只计一次。
- 累计值下降、累计字段缺失、文件截断时保持明确的兼容行为。
- 在 UTC、洛杉矶和上海时区下，北京时间 00:30 的记录都归入同一个北京时间日期。
- 最近 31 日、昨日和默认查询年份在非北京时间系统时区下仍以北京时间为准。
- 对同一静态 fixture 连续执行两次手动全量同步，三项汇总完全一致。
- 全量测试与 renderer 构建继续通过。

## 验收标准

- 同一份 Codex/Kimi 静态日志连续重扫两次，`usageDaily` 完全一致。
- Codex 重扫结果不包含累计值未变化的重复 `token_count`。
- 约 938 MiB 的现有 Codex 日志不会因为 200 轮限制被当作已完成。
- 手动同步和后台轮询并发触发时，不重复累加日志区间。
- 操作系统时区不是中国标准时间时，每日结算仍以北京时间 00:00 为边界。
- 同步失败后，用户仍看到同步前的完整 provider 数据。
- 升级后不自动重扫或修改现有统计；用户手动同步后才替换旧数据。
