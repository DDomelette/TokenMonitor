# Codex 归档日志用量重建与稳定游标设计

## 背景

Codex 本地用量来自 rollout JSONL 中的 `token_count` 事件。当前实现只扫描
`~/.codex/sessions/**/rollout-*.jsonl`，并以文件绝对路径保存读取 offset。
Codex 会话系统把旧 rollout 移入 `~/.codex/archived_sessions` 后，应用既无法继续读取
尚未扫描的尾部，也会删除已经消失的旧路径游标。

本机事件级复算确认了由此造成的历史缺口：

- 2026-08-09：store 为 511,469,846，去重后应为 586,611,582；
- 2026-08-11：store 为 671,894,456，去重后应为 811,957,820；
- 2026-07-23：store 多计 388,495，去重后应为 640,925,483；
- 2026-08-10：store 与去重结果均为 57,881,312。

归档文件中可能同时含有移动前已经计入的前缀和从未计入的尾部。因此不能直接把归档
目录总量加进现有 store，也不能在缺少旧 offset 的情况下对归档目录做普通增量扫描。

## 目标

本次采用 A+B 方案，同时完成以下目标：

1. 升级后自动用活动目录和归档目录的全部 rollout 事件级去重重建 Codex 历史用量。
2. 重建成功前保持旧统计可见；失败不修改旧数据，并在下次启动重试。
3. 将 Codex 游标改为按 rollout UUID/文件名稳定追踪，使文件移动后从原 offset 续扫。
4. 日常扫描同时覆盖活动和归档目录，不因移动、短暂双份或扫描批次边界重复计数。
5. 只替换 `codex:*` 日数据，保留 DeepSeek、Kimi、设置和其他持久状态。

## 非目标

- 不建立永久事件数据库或长期保存所有事件指纹。
- 不修改、移动或清理原始 rollout 文件。
- 不改变 DeepSeek、Kimi 的日志目录、游标或统计口径。
- 不改变现有 Token 总量、缓存和输出字段口径。
- 不扩大或缩小 `data.historyDays`；自动迁移负责准确重建全量，后续仍由现有保留机制清理。
- 不要求正在持续写入的“今天”在两个非原子快照间瞬时完全相等。

## 方案选择

采用“影子重建 + 稳定文件游标”。后台迁移先在独立内存状态中得到完整 Codex 汇总和
最终游标，再以一次 store 快照写入提交。日常扫描用 rollout 稳定身份联合扫描两个目录。

未采用原地清空重扫，因为进程中止时会留下空数据或半套数据。未采用永久事件账本，
因为迁移期全局去重与日常相邻事件去重已经覆盖已知问题，永久索引的存储和迁移成本
超出本次范围。

## 目录解析

Codex 默认日志源为：

- 活动目录：`~/.codex/sessions`；
- 归档目录：`~/.codex/archived_sessions`。

现有 `providers.codex.localLogRoot` 继续表示活动目录。若用户配置了自定义活动目录，应用
不会猜测其父目录结构；只有显式设置新的 `providers.codex.archivedLogRoot` 时才启用对应
自定义归档目录。未配置自定义活动目录时，默认归档目录自动启用。

文件监听仍是降低延迟的加速器，60 秒调度扫描是完整性兜底。活动文件移走会在活动目录
产生变更事件并触发联合扫描；即使监听器漏报，下一次定时扫描也会发现归档文件。

## 稳定文件身份与候选选择

rollout 文件身份优先取文件名末尾 UUID，例如：

```text
rollout-2026-08-09T19-01-47-019fe62f-9a3c-7cb2-9e34-f21173cf257d.jsonl
                            └────── stable rollout id ──────┘
```

文件名不符合标准 UUID 格式时，退化为完整 basename。绝对路径只能作为本轮打开文件的
候选位置，不能作为持久游标键。

每轮扫描先完整枚举两个根目录，再按稳定身份分组：

- 只有一个候选时直接使用；
- 两个目录短暂存在同一身份时只选一个候选；
- 大小不同时优先选择能够承接已有 offset 且 size 最大的候选；
- 大小相同时优先活动目录，保证选择确定；
- 同一身份候选的头部指纹冲突时记录诊断，按确定顺序选择并按替换文件处理。

文件在枚举与打开之间移动时，扫描器按稳定身份重新枚举一次候选。找到新位置后继续；
两个位置都不存在时跳过本轮。只有联合枚举完成后确认某身份在两个目录都不存在，才清理
该身份游标。

## 游标数据模型

Codex 新游标继续存放在 `localLogCursors.codex`，但键和值改为：

```js
{
  "019fe62f-9a3c-7cb2-9e34-f21173cf257d": {
    offset: 123456,
    mtimeMs: 1786500000000,
    size: 234567,
    headFingerprint: "sha256:...",
    lastEventFingerprint: "sha256:..."
  }
}
```

字段语义：

- `offset`：最后一个已提交完整换行之后的字节位置；
- `mtimeMs`、`size`：诊断及候选选择信息；
- `headFingerprint`：文件头固定小块的 SHA-256，用于识别同名文件替换；
- `lastEventFingerprint`：最后一个已处理 `token_count` 的事件指纹，用于跨批次相邻去重。

文件 size 小于 offset、头部指纹改变或候选无法承接 offset 时，从零开始并清空
`lastEventFingerprint`。单纯路径变化或 mtime 变化不重置 offset。

## 事件指纹与去重

事件指纹由以下规范化字段计算 SHA-256：

```text
timestamp \0 input_tokens \0 cached_input_tokens \0 output_tokens
          \0 reasoning_output_tokens \0 total_tokens
```

缺失的数值字段规范化为零。`rate_limits`、累计快照和其他易变元数据不进入指纹，使同一
token 增量即使附带不同限额快照也仍被识别为重复。

日常增量扫描只持久化 `lastEventFingerprint`。当前事件与它相同时，游标正常越过该行，
但事件不进入汇总；事件改变后正常计入并更新指纹。这覆盖同一文件内相邻重复事件以及
重复事件跨越 4 MiB 扫描批次的情况，而无需永久事件集合。

自动全量迁移和手动全量重建在内存中持有本次扫描的全局事件指纹集合。两个目录、两个
候选或同一文件任意位置出现相同事件时只计一次。集合在重建成功或失败后释放，不写 store。

## 扫描接口与完成状态

通用扫描核心增加批次结果接口，返回：

```js
{
  records: UsageRecord[],
  complete: boolean,
  bytesRead: number
}
```

`complete` 表示已经覆盖本轮联合枚举快照中的所有候选和可提交完整行。达到 4 MiB 预算
返回 `complete=false`，即使本轮没有解析出用量记录也不能把全量重建视为完成。

现有单目录 `scanFiles()` 行为保留为兼容包装，Kimi 继续使用路径身份。Codex 联合扫描
使用同一底层分块读取原语，但注入稳定身份、候选集合和事件去重函数。

全量重建循环到 `complete=true`。保留明确的安全轮数/字节上限；耗尽仍未完成时抛出
`LOCAL_LOG_RESCAN_INCOMPLETE`，不得提交部分结果。

## 后台自动迁移

迁移完成标记为：

```text
localLogMigrations.codexArchiveUuidCursorV1
```

启动时未发现标记便创建唯一的迁移 Promise，并将 Codex 置为 `migration-pending`：

- dashboard 继续读取旧 `usageDaily`；
- Codex 定时扫描、文件监听触发和手动增量刷新等待该 Promise，不另起写入；
- DeepSeek、Kimi、配额查询和其他功能继续运行。

迁移使用空的影子 `usageDaily`、空 UUID 游标和全局事件指纹集合联合扫描两个目录。扫描
不受 `data.historyDays` 过滤。完成后得到完整 `codex:*` 日汇总和指向扫描快照末尾的游标。

提交时重新读取最新的 `store.store`，在没有 `await` 的同步临界区内构造下一份完整快照：

1. 删除其中所有旧 `codex:*`；
2. 合并影子 `codex:*`；
3. 设置 UUID 游标；
4. 设置迁移完成标记；
5. 通过一次 `store.store = nextStore` 写入。

在提交瞬间重新读取 store，可保留迁移期间 DeepSeek、Kimi、设置或窗口状态的更新；单次
完整快照写入保证 Codex 汇总、游标和迁移标记不会分步提交。

提交成功后解除暂停，立即运行一次普通 Codex 联合增量扫描，补上影子枚举快照后新追加
的完整行，再广播 dashboard 刷新。

## 失败与兼容模式

影子扫描、解析、候选重试或 store 提交任一步失败时：

- 不修改旧 `usageDaily`、旧路径游标或迁移标记；
- 错误日志只含错误类别和计数，不输出会话内容或完整私有路径；
- 当前进程解除 Codex 暂停，并进入旧版兼容模式：只扫描活动目录、继续使用旧路径游标；
- 下次启动因迁移标记仍缺失而重新尝试影子迁移。

Codex provider 根据迁移标记选择模式：标记存在时使用双目录 UUID 游标；标记不存在且
没有迁移持锁时使用旧活动目录路径游标。影子迁移显式使用 UUID 模式，与旧游标隔离。

## 手动历史同步与并发

自动迁移、Codex 手动历史重建和 Codex 增量扫描共享同一运行时独占协调器：

- 自动迁移运行时，手动同步等待并复用同一 Promise；
- 自动迁移成功后，手动同步使用双目录、全局事件去重的影子重建路径；
- 自动迁移失败后，用户手动同步可以显式重试同一安全迁移，而不是原地清空；
- 定时轮询和文件监听触发在全量重建期间等待，不并发读取和累加；
- 不同 provider 继续互不阻塞。

对已迁移用户，手动重建也使用影子状态和一次完整 store 快照提交。失败保留同步前完整
数据和游标。

## 组件边界

### `src/main/core/locallog.js`

负责通用分块读取、完整行提交、扫描预算和明确完成状态。保留单目录兼容入口，提供可由
Codex 注入稳定身份和候选列表的批次原语。

### `src/main/providers/codex/locallog.js`

负责默认活动/归档根目录、rollout 身份解析、候选分组、事件指纹、双目录增量扫描和旧版
路径模式兼容。Kimi provider 不依赖这些 Codex 专用规则。

### `src/main/providers/codex/migration.js`

新增独立模块，负责影子 store、全局事件去重、全量循环、Codex 数据快照替换、迁移状态
和唯一 Promise。迁移模块不修改原始日志。

### 启动、调度和 IPC

启动流程创建迁移协调器并在后台启动。调度器在进入 Codex localLog channel 前经过协调器；
历史同步通过协调器调用安全影子重建。文件监听最终仍通过调度器触发，不绕过独占规则。

## 测试设计

测试采用 Node 内置 test runner 和临时目录，遵循红—绿—重构流程，至少覆盖：

1. 已读部分文件从活动目录移动到归档目录后只返回尾部事件。
2. 同一 UUID 在两个目录短暂共存时只扫描一次。
3. 同一 UUID 候选大小不同、文件截短、头部替换和打开前移动的处理。
4. 重复事件在同批次、跨 4 MiB 批次和两个候选中只计一次。
5. 无用量记录但读取了字节的批次不会让全量扫描提前结束。
6. 影子重建只替换 `codex:*`，完整保留 DeepSeek、Kimi 和其他 store 键。
7. 扫描失败和 store 提交失败都保持原数据、旧游标和缺失的迁移标记。
8. 迁移成功后汇总、UUID 游标和完成标记在同一 store 快照出现。
9. 迁移失败后恢复活动目录旧版扫描，下次启动仍会重试。
10. 自动迁移、手动同步和定时轮询不能并发写 Codex 数据。
11. 对相同静态日志连续影子重建两次，汇总和游标一致。
12. 现有 Kimi、保留窗口、分块扫描、设置重置和诊断测试保持通过。

## 验收标准

- 升级首次启动时旧统计保持可见，其他 provider 正常工作。
- 迁移成功后上述历史日期与事件级去重基准一致。
- 迁移过程中终止进程或触发扫描/提交失败，不留下半套 Codex 数据。
- rollout 在两个目录间移动后，下一次扫描从原 offset 继续，不重读已计前缀。
- 同一静态日志连续重建两次得到相同日汇总。
- 迁移完成后的普通增量扫描不会再次累计已重建事件。
- 完整 Node 测试套件和 renderer 构建通过。
